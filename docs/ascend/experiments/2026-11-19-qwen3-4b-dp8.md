# Experiment record: Qwen3-4B on eight 910B3 cards

A standalone record of one optimization session: what was deployed, what was measured, what the session kept, and
what it could not explain away. It complements the status document at [../README.md](../README.md).

## Objective

Measure whether `hyperloom optimize` finds a throughput gain for a small dense model spread across eight NPUs,
using the deployment shape the vLLM-Ascend Qwen3-Dense tutorial recommends.

## Setup

| Item | Value |
|---|---|
| Accelerators | 8 × Ascend 910B3, 64 GiB HBM each, one node |
| Model | Qwen3-4B-Instruct-2507 (36 layers, GQA 32 heads / 8 KV heads, bf16) |
| Stack | CANN 9.2.0, vLLM 0.30.0, vllm-ascend 0.30.0, torch 2.10, torch_npu 2.10 |
| Shape | eight data-parallel replicas, one per card (`--data-parallel-size 8 --tensor-parallel-size 1`) |
| Launch | `--distributed-executor-backend mp`, `HCCL_OP_EXPANSION_MODE=AIV`, `PYTORCH_NPU_ALLOC_CONF=expandable_segments:True` |
| Workload | ISL/OSL 1024, concurrency 256, 320 requests per round, prefix caching on |
| Accuracy gate | GSM8K, 5-shot, 64 samples |
| Budget | 2 h wall clock |

The base launch script the session resolved:

```bash
export ASCEND_RT_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
export HCCL_OP_EXPANSION_MODE=AIV
export PYTORCH_NPU_ALLOC_CONF=expandable_segments:True

vllm serve <Qwen3-4B path> \
  --served-model-name qwen3-4b \
  --trust-remote-code \
  --distributed-executor-backend mp \
  --data-parallel-size 8 \
  --tensor-parallel-size 1 \
  --max-model-len 8192 \
  --max-num-batched-tokens 8192 \
  --max-num-seqs 64 \
  --gpu-memory-utilization 0.85 \
  --compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY"}'
```

A small dense model fits on one card, so the eight-card shape is eight replicas rather than tensor parallelism; the
per-replica batch is what has to be tuned, not the shard width.

## How the session was run

`hyperloom optimize` drives the whole loop — baseline round, accuracy gate, the coordinator's `explore` proposals,
per-candidate KEEP/REVERT, and a final report. The session has to outlive the shell that starts it, so it ran under a
transient systemd unit:

```bash
systemd-run --unit=hl-qwen34b --collect --working-directory=<repo> <runner script>
```

The runner exports `KERNEL_AGENT_ENV` (the kernel-agent env file), `INFERENCE_SUITE_TOOL_CACHE` (the staged
InferenceX subset) and `HYPERLOOM_EVAL_LIMIT=64`, then invokes:

```bash
python -m hyperloom optimize \
  --framework vllm --model <Qwen3-4B path> --reference-script <base launch script> \
  --tp 1 --conc 256 --isl 1024 --osl 1024 --max-model-len 8192 --gpus-per-node 8 \
  --max-hours 2.0 --no-kernel --no-enable-roofline --enablement off
```

The session seeded its first grid from the vLLM-Ascend levers (decode-only graph, reserve-ISL scheduler switch,
batch caps, prefix caching), then proposed a second grid from its own analysis.

## Results

Baseline **9934.3 tok/s**, best **10937.9 tok/s**, `cumulative_gain_val` **10.10%** (validated against a re-measure of
the kept stack), baseline accuracy 0.90625 → kept-stack accuracy 0.921875.

| Candidate | tok/s | vs baseline | Verdict |
|---|---:|---:|---|
| baseline | 9934.3 | — | — |
| `--no-scheduler-reserve-full-isl` | 10314.7 | +3.83% | **KEEP** |
| `VLLM_USE_V2_MODEL_RUNNER=1` (on top of the keep above) | 10937.9 | +6.04% | **KEEP** |
| `--max-num-batched-tokens 16384` | 10303.5 | +3.7% | REVERT (below the bar against the then-current best) |
| `--max-num-seqs 512` | 9964.1 | +0.3% | REVERT |
| `--no-enable-prefix-caching` | 9922.7 | −0.1% | REVERT |
| `nz-bf16-weights` | 9563.0 | −3.7% | REVERT |
| `aclgraph-static-kernel` | 10299.4 | +3.7% | REVERT |

`stop_reason=time_exhausted`: the budget ran out while the coordinator was still proposing candidates, not because the
search converged.

## What the numbers say

- The two keeps are **defaults that do not fit this shape**, not tuning: the reserve-full-ISL scheduler caps
  concurrency for a small model that has KV to spare, and the v2 model runner removes per-step overhead. Both improve
  accuracy in this run rather than trading it away.
- The tutorial's headline knobs were already neutral here. Decode-only graph mode was in the baseline; `max-num-seqs`
  does not bind at 32 requests per replica; disabling prefix caching is flat; `nz`-layout bf16 weights are slower.
- Taken with the single-card Qwen3-8B result in [../README.md](../README.md) §6, the pattern is that the parameter
  layer rewards fixing wrong defaults and little else; the remaining headroom is quantization and shape.

## Incidents during the run

Two host changes broke the ad-hoc verification path afterwards, and both are worth recording because they will bite
again:

1. **The toolkit's `latest` link was repointed to a 9.3.0 install that lacks `runtime`, `compiler` and `opp` under
   `aarch64-linux/`**, so `torch_npu` failed with `libhccl.so: cannot open shared object file`. Pinning the 9.2.0
   tree (and adding the missing sub-directory links) restored `torch_npu`.
2. **The environment carries `triton` 3.5.0 while vLLM 0.30 expects 3.4** (`constexpr_function` is gone from
   `triton.runtime.jit`). With `HAS_TRITON=False`, vllm-ascend never registers `qkv_rmsnorm_rope`, and a Qwen3 serve
   dies with `'_OpNamespace' 'vllm' object has no attribute 'qkv_rmsnorm_rope'`. The session above ran before this
   drift, so its numbers stand; a fresh two-arm re-measure needs the triton pin fixed first.

## Reproduction

1. Resolve the base from the launch script: `inference_suite resolve --query <query.json> --gpus 8 --user-file <launch script> --out <base_launch.json>`.
2. Run one round to confirm the shape: `inference_suite run --config <config.yaml> --run-dir <dir>`.
3. Run the session under systemd with the command above; watch `state.json` for `optimization_stack` and the final
   report for `cumulative_gain_validated`.
